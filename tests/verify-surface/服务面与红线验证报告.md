## 一、红线静态复核：「未装 GUIFrame 时页面照常启动」—— **结论：成立（静态面已复核，真机面留收口）**

红线原文（GB15 + Q16 强化）：插件可以用本插件的接口与组件，但不能变成「不装本插件就启动不了」；依赖缺失时插件不激活、不占座位，且页面必须照常启动。

**结论一（未装 = 零影响，成立）**：本包的唯一注册通道是 `cordis.patch.yml` 里的一行 `- insert: {id: gui-frame, name: dsh-gui-frame}`，而它只有在 profile 的 `dsh.profile.bundles` 点名本包时才会被装载器取用。本机 `~/.dsh/profiles/web` 实测：**本包不在 bundles 里，profile 的 `cordis.patch.yml` 里也没有 `gui-frame` 的 insert 行** ⇒ 组合里根本没有本插件 ⇒ 本包零代码执行，页面行为与未装完全一致。判据 [T18-⑧a]（`tests/verify-surface/redline-static.test.mjs`）。

**结论二（装了/降级也不许打死页面，成立）**：t4 探针给出的两条「整页失败」机制是 ——
① 客户端 `apply` 抛错 ⇒ `loader.create` 拒绝冒泡出 `runPluginBoot` 的 `Promise.all`（无 try/catch）⇒ `page.fail` 且 `mountApp` 永不执行；
② 声明 `inject` 而服务缺席 ⇒ fiber `pending` ⇒ `assertEntriesActive` 抛错。
对这两条，本包在静态上各堵死一路：客户端入口与宿主半区的 `inject` **恒为空数组**（结构性不可能 pending）；`apply` 同步返回 `undefined` 且当前零注册；`provideService(ctx)` 在「服务名已被占用」与「provide 自身抛错」两种情况下都**让位返回 `owned:false`，绝不 rethrow**（源码级 catch 块扫描 + 行为级各一次）。判据 [T18-⑧b]，另见 [T18-④c]。

**这条红线的边界（不许当成已验证）**：真正的「浏览器里装上本包、页面照常起」要等真机装载（`npm run link` → `dsh plugin --profile web add …`），按纪律留到收口时由用户在场执行；本报告只承担**静态面**的结论。t4 的 P1/S1、P1/S3 两条机制物证来自**真平台库复现**（已由 [T18-⑦b] 在本机重跑复现），不是文档转述。
