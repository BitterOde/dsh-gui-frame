## P1 · 客户端 apply 抛错是否真打死整页 —— 判定：**是，整页失败；但机制与家族二手转述不同**

### 可重演步骤

1. `node probe/runtime/apply-throw-probe.mjs`。
2. 脚本跑三个场景，全部走外壳真路径（`runPluginBoot` → `loader.create({name})` → `loader.await()` → `assertEntriesActive`）：
   - **S1**：模块表里有 `@probe/ui-renderer`（提供 `uiRenderer`）、`@probe/ok`（正常）、`@probe/boom`（`apply` 必抛）。
   - **S2**（**改动版，只用于观察**）：手工 `await ctx.loader.create({name:'@probe/boom'})` 并吞掉拒绝，再单独调 `assertEntriesActive`。
   - **S3**：`@probe/needs-frame` 声明 `inject: ['gui-frame']` 而无人提供（Q16 场景）。
3. 看 `probe/evidence/p1-apply-throw.json` 的 `appMounted` / `pageFailure` / `page.states` / `entriesAfterBoot`。

### 观察结果（原文摘录）

| 场景 | appMounted | page.fail 文案 | 入口最终状态 |
| --- | --- | --- | --- |
| S1 | **false** | `web boot: 1 entry did not activate\n@probe/boom: failed` | `@probe/ui-renderer=active`、`@probe/ok=active`、`@probe/boom=failed`（entry **留在树里**，不再被删） |
| S2 | — | `createError=null`；`entriesAfterCreate=[{id:'@probe/boom',fiberState:'failed'}]`；`auditError=web boot: 1 entry did not activate\n@probe/boom: failed` | 失败入口留在树里并被审计点名（旧版行为是 create 抛错 + entry 被删、审计无对象） |
| S3 | **false** | `web boot: 1 entry did not activate\n@probe/needs-frame: pending (waiting for service: gui-frame)` | `@probe/needs-frame=pending`，`needsFrameAppliedCount=0` |

S1 的状态迁移流水（`page.setState` 记录，逐条来自真 `internal/status` 事件）：

```
setTotal 3
@probe/ui-renderer=loading → @probe/ok=loading → @probe/boom=loading
@probe/boom=unloading
@probe/ui-renderer=active → @probe/ok=active
@probe/boom=failed
console.error(<updateError 栈>)   ← 唯一对外可见面：浏览器控制台
page.fail("web boot: 1 entry did not activate\n@probe/boom: failed")
```

### 判定

1. **apply 抛错 = 整页失败，不是"少一块功能"。** 机制（两处，都在外壳 boot kernel 原文里）：
   - `runPluginBoot`（0.2.0 外壳产物里的 `JS`）里 `await Promise.all(ids.map(async id => { … await loader.create({name:id}) … }))` **没有任何 try/catch**；
     **0.2.0-rc.2 实测**：`loader.create` 不再把启动失败包成 `failed to apply loader entry …` 抛出，而是把 entry
     留在树里、fiber 标 `failed`（S2 的 `createError=null` + `entriesAfterCreate=[…failed]`）；
     随后外壳的 `assertEntriesActive`（`eM`）扫全树，把非 active 的条目聚合成
     `web boot: N entries did not activate\n<id>: <state>` 抛出（见 `probe/evidence/p1-apply-throw.json`）。
     旧版（0.1.5-rc.3）是 `loader.create` 直接抛 `failed to apply loader entry <id> (<name>): <cause>` 且 entry 被删
     —— 两种形状都整页失败，差别只在"失败 entry 还在不在树里"。
   - 该错误冒泡出 `runPluginBoot` → 被 `run()` 的 `catch` 接住 → `console.error(t)` + `page.fail(msg)`，
     **`await this.mountApp(a)` 永不执行** ⇒ `uiRenderer.mount(container)` 从未发生 ⇒ 页面停在启动遮罩的失败卡片
     （`tM.fail()` 渲染 "Failed to load plugins" + 各失败入口名，见 `probe/evidence/shell-boot-overlay.txt`）。
   - 也就是说：**家族旧结论"会打死整页"成立**；"由 `assertEntriesActive` 审计打死"这半句在 0.2.0 上**反而成立**
     （失败 entry 留在树里、审计点名它），但整页失败的**直接原因仍是 `mountApp` 不执行**，不是审计本身。
2. **失败入口即使留在树里（旧版是被删），页面也不会自愈**：S1/S3 都没有第二春；`mountApp` 是单次顺序调用。
3. **对有依赖的插件（Q16 的载体）**：S3 复现了 Q16 的机制 —— 声明 `inject` 而服务不存在 ⇒ fiber 停在 `pending` ⇒ `assertEntriesActive` 抛
   `web boot: 1 entry did not activate / <id>: pending (waiting for service: gui-frame)` ⇒ 同样整页失败。**Q16 的二手转述本轮实测成立**。
4. **对 GUIFrame 的直接后果**（交给 t12/t16 的实现纪律）：
   - GUIFrame 自己**没有任何"抛错的权利"**：`apply` 里任何未捕获异常都会打死整页（含它没装/装了别人的场景）。
     必须整体 `try/catch`：捕获后走自有错误态 + `console.error` + （阶段 2）上报，**绝不 rethrow**。
   - 反向同理：**GUIFrame 不得让别的插件因它而 pending** —— 这正是 Q16 的红线（逃生写法 `ctx.get('gui-frame')`），S3 给出了"不遵守会怎样"的物证。

### 残余未知 + 真机收口（P1）

- 未做：浏览器真机渲染（失败卡片像素、DevTools 里的 `console.error` 原文）。脚本层用记录桩代替了 DOM。
- 收口步骤（**用户在场**，可在不打断当前 GUI 的前提下另开一个临时 profile 做，或按收口轮统一安排）：
  1. 在临时 profile 装一个「`apply(){ throw new Error('probe-p1') }`」的客户端插件（id 随意），`dsh web` 打开页面。
  2. 预期：**页面停在启动卡片并显示 "Failed to load plugins" + 该 entry 名**（0.2.0 的形状是 `@probe/boom: failed` 这一段；旧版是 `failed to apply loader entry …: probe-p1`）；不出现会话界面；DevTools Console 第一条红字含同一段聚合文案。
  3. 卸载该插件 → 重启 → 页面恢复正常，证明失败只由该 entry 引起、页面本身没坏。

## P2 · Q17 上报链路：`process.stderr.write` 那条路真的必达吗 —— 判定：**必达（两段机检通过）；`ctx.logger` 那条路连内存 buffer 都不一定进**

### 可重演步骤

1. `node probe/runtime/log-channel-probe.mjs`（父进程）；它用 `spawnSync` 各跑一次同一子进程 `probe/runtime/log-channel-child.mjs`：
   - **pipe 档**：父进程分别持有子进程的 stdout/stderr 两条管道 → 逐字节搜哨兵串；
   - **inherit 档**：子进程 stderr 直接继承本探针进程 → 那行哨兵会出现在你眼前（本次运行已出现）。
2. 子进程做两件事：真 cordis 根 ctx 上 `logger.error/info/warn/debug(同一哨兵)`，然后 `process.stderr.write('[gui-frame] 客户端失败 stderr-marker-P2')`。
   哨兵原文**只**写进 logger/stderr，绝不落到 stdout，父进程才能把"搜不到"当证据。

### 观察结果（原文摘录）

```
P2-CHILD {"exporters":1,"bufferLen":2,"bufferTypes":["error:0","info:1"],
          "errorHitsBuffer":true,"infoHitsBuffer":true,"warnHitsBuffer":false,"debugHitsBuffer":false,
          "loggerLevel":null,"loggerName":"root"}
  PASS  A1 子进程 logger 写的哨兵没出现在 stdout
  PASS  A2 子进程 logger 写的哨兵没出现在 stderr
  PASS  A3 默认配置下 logger.error 进内存 buffer
  PASS  A4 默认配置下 logger.warn 连内存 buffer 都进不去
  PASS  A5 默认配置下 logger.debug 连内存 buffer 都进不去
  PASS  B1 process.stderr.write 的哨兵出现在 stderr 管道
  PASS  B2 该哨兵不串到 stdout
子进程 stderr 转录：[gui-frame] 客户端失败 stderr-marker-P2
inherit 档（若你看到这行，说明 stderr 写真的到了终端）：[gui-frame] 客户端失败 stderr-marker-P2   ← 已在本轮命令输出里出现
```

### 判定

1. **`process.stderr.write` 必达**：写入 → 子进程 stderr 管道拿到（B1）→ inherit 档直落终端（本轮肉眼可见）。这是本机同一 node 进程模型下"字节确实离开了进程"的机检证据，不是推断。
2. **`ctx.logger` 不能当上报通道**（比 GS11 现有措辞更严）：
   - 全树只注册了 **1 个 exporter**（`exporters:1`）——Cordis 内置内存 buffer（`LoggerService` 构造器自注册，`cordis/lib/index.js` L583-606，见 `probe/evidence/cordis-logger-buffer-exporter.txt`）；**没有任何 stdout/stderr exporter**（在整棵 DSH 安装树里 `grep '\.exporter('` 只命中三处：cordis 宿主侧的注册与 `exporter()` 方法体各一处，以及外壳产物里同一份 cordis 的浏览器副本 —— 都没有面向终端）。
   - 更关键：默认级别阈值取 `exporter.levels?.[name] ?? exporter.levels?.default ?? this.level ?? 1`（`cordis/lib/index.js` L473-474，见 `probe/evidence/cordis-logger-threshold.txt`），
     **实测 `warn`(2)、`debug`(3) 连 buffer 都进不去，只有 `error`(0) 与 `info`(1) 会留在 buffer 里**（A3/A4/A5）。
   - 本机 web profile 未配置 `logger:` 级别（`~/.dsh/profiles/web/cordis.patch.yml` 无该键，`cordis.yml` 为 `[]`），故默认口径成立。
   ⇒ **结论：cmd 里想看见，就必须自己 `process.stderr.write`；只 `ctx.logger.warn(...)` 等于什么都没发生。**
3. **宿主侧这条腿（route → 同进程 → stderr）机制成立**：
   - 宿主半区 `ctx.connection.fetch.register({path, methods, requestBody, fetch})` 把精确路由存进 `fetchRoutes`，由 `/api` 共享通道的 `createSharedFetchHandler(API_PATH)` 在**同一个 node 进程里**同步分派
     （`dsh-client-connection/lib/index.js` L573-600、L750-782，见 `probe/evidence/connection-fetch-route.txt` / `connection-fetch-dispatch.txt`）。
   - 分派前过 `connection.requestRejection(req)`（Host/Origin fence + 浏览器认证）——页面同源 POST 走的就是它自己应用流量的同一条围栏。
   - **平台先例**：DSH 自己在宿主侧也是这么写的 —— `installFailLoud` 里 `proc.stderr.write(\`${binName}: fatal load failure: …\`)`（`dsh-app-boot/lib/index.js` L1401-1408，见 `probe/evidence/app-boot-installFailLoud.txt`）。我们自己写 stderr 与平台同源同理。
4. **可达性的真实边界（Q17 那条"最严重场景会失效"的边界，本轮给出物证）**：
   - **boot 阶段崩的页面确实上报不了**：P1 已证 `mountApp` 不执行 ⇒ 应用（含连接）没挂起来；此时能救场的只有"GUIFrame 自己 `apply` 里 try/catch 并在 catch 里立刻发 `fetch`"这一档
     （浏览器 JS 上下文未被销毁、HTTP 服务仍在），**但这条"catch 里的 fetch 能发出去"依赖浏览器行为，本轮没真机验过**，列为收口项。
   - 反过来：**P1 的 S3（被别人的 pending 拖死）与 P1 的 S1（别人 apply 抛错）这两档，GUIFrame 自己没有代码在跑，必然上报不到** —— 这不是实现问题，是外壳的失败模型决定的，应当写进接入文档而不是靠上报兜。

### 残余未知 + 真机收口（P2）

- 未做（不碰在跑进程，故不做）：正在跑的 `dsh web` 那个控制台窗口是否确实收到 `process.stderr.write`。
- 收口步骤（**用户在场**；安排一次「装 GUIFrame → 故意降级 → 看 cmd」）：
  1. 打开当前 GUI（127.0.0.1:3080），确认它是由某个 cmd/pwsh 窗口启动的（该窗口此刻能看到 DSH 的启动横幅即证明 stdout/stderr 指向同一控制台）。
  2. 触发一次"客户端失败"（t16 会提供 demo 里的降级开关；或临时把 diagnostics 上报端点打开）。
  3. 预期：**该 cmd 窗口出现一行 `[gui-frame] 客户端失败 …`**；同时页面内应有自有错误态、DevTools 应有一条 `console.error`。
  4. 反证：同一动作若只走 `ctx.logger.warn`（临时把 stderr 那行注释掉），**cmd 窗口应一片安静** —— 这一正一反两条都留证，才算了结 Q17。

## P3 · GUIFrame 卸载后，已自检（inject）的插件会怎样 —— 判定：**effect 被卸载 → 回 pending（entry/fiber 保留）→ 服务回来自动重新 apply**

### 可重演步骤

1. `node probe/runtime/unload-remount-probe.mjs`。
2. 三条真入口（走外壳同一条装载路径）：`@probe/frame`（提供 `gui-frame`，GUIFrame 位）、`@probe/consumer`（`inject:['gui-frame']`，第三方位）、`@probe/getter`（只 `ctx.get('gui-frame')`，Q16 逃生写法）。
3. 时间线：装好 → `loader.remove(frameEntryId)` → 再 `loader.create({name:'@probe/frame'})`；每步记录 fiber 状态、uid、apply/卸载计数、effect 存活数。

### 观察结果（原文摘录，`probe/evidence/p3-unload-remount.json`）

```
状态迁移（真 internal/status 事件，逐条）：
  @probe/frame: loading(uid=3) → active(uid=3)
  @probe/consumer: loading(uid=4) → active(uid=4)
  @probe/getter: loading(uid=5) → active(uid=5)
  @probe/frame:   unloading(uid=null)
  @probe/consumer: unloading(uid=4) → pending(uid=4)      ← 卸载 GUIFrame 的连锁
  @probe/frame:   disposed(uid=null)
  @probe/frame:   loading(uid=6) → active(uid=6)          ← 装回来是一个新 fiber
  @probe/consumer: loading(uid=4) → active(uid=4)         ← 依赖方自动重挂载

计数：① 装好      {frameApplies:1, frameEffectsAlive:1, consumerApplies:1, consumerEffectsAlive:1, consumerSawService:[true]}
      ② 卸载后    {frameApplies:1, frameUnloads:1, frameEffectsAlive:0, consumerApplies:1, consumerUnloads:1, consumerEffectsAlive:0}
      ③ 装回来    {frameApplies:2, frameEffectsAlive:1, consumerApplies:2, consumerEffectsAlive:1, consumerSawService:[true,true]}
③ 的 entry 表：consumer=active(uid=4 不变)、getter=active(uid=5 不变)、frame=active(uid=6 新)
```

### 判定

1. **三者都发生，按顺序**：`inject: ['gui-frame']` 的插件在提供方卸载时**先被卸载（effects 全部清理：consumerEffectsAlive 1→0）**，**再回到 `pending`（fiber 与 entry 保留，uid 不变）**，**服务重新出现时自动重新 `apply`**（`consumerApplies` 1→2，且新一次 `apply` 里 `ctx['gui-frame']` 确实有值）。机制在 `Fiber._refresh/_setEpoch/_unload`（`cordis/lib/index.js` L1316-1391，见 `probe/evidence/cordis-fiber-inject-lifecycle.txt`）：epoch 由提供方 fiber uid 拼成，服务消失 ⇒ epoch=INACTIVE ⇒ 卸载并落 `pending`；服务回归 ⇒ epoch 变化 ⇒ `_reload`。
2. **不是"被彻底卸载"**：entry 仍在 loader 树里（③的 entry 表可证），依赖方 fiber 复用（uid=4 前后一致）。
3. **`ctx.get('gui-frame')` 逃生写法零耦合**：getter 全程 `active`、`getterUnloads=0`、`apply` 不再跑 —— Q16 推荐的写法在生命周期上是干净的（页面不会因为它而进入 pending）。
4. **运行期卸载不会打死页面**：`assertEntriesActive` 只在 boot 跑一次；运行期把 GUIFrame 卸掉，依赖方停在 pending（不注册、不占座位），页面继续跑。**唯一要守住的仍是"boot 时不能 pending"**（P1 S3）。
5. **给实现的两条硬性后果**：
   - GUIFrame 的 `provide('gui-frame', …)` 必须挂在**它自己 fiber 的 effect** 上（`ctx.provide` 天然如此），卸载要**干净注销**；否则依赖方会停在 pending 且重挂载后残留双份。
   - GUIFrame 侧任何"跨卸载存活的全局态"都会在 ③ 的自动重挂载里被二次进入 —— 重挂载必须是幂等的（这条直接约束 t3 的 `register`/`overlay` 与 t15 的恢复屏障）。

### 残余未知 + 真机收口（P3）

- 未做：浏览器真机里的同一序列（理论上同一份 vendored loader 代码路径：外壳 `loader.internal = ClientModuleSystem`，`internal.import` 返回 bundle 工厂的 exports，与探针的模块表同契约 —— 但**没在浏览器里跑过**）。
- 收口步骤（**用户在场**，收口轮统一安排）：
  1. 装 GUIFrame + 一个 `inject:['gui-frame']` 的试验插件（或直接看 GUIFrame 自己的坞/面板是否消失与回归）。
  2. `dsh plugin remove`（或 patch 里注释掉 insert 行，live reload）→ 预期：**页面不崩**，试验插件的入口/面板消失（effects 被清），DevTools 里该插件无残留节点。
  3. 装回来 → 预期：**入口/面板自动回来**，且不出现重复注册（坞里一份、没有幽灵层）。
