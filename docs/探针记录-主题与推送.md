## P4 · 主题 token 口径对齐 —— 判定：**不是"谁对谁错"，是四个不同集合；lint 的白名单真源不是 `exportInspectTokens()`**

### 可重演步骤

1. `node probe/runtime/theme-token-probe.mjs`。
2. 脚本对同一份产物分别数四个口径：
   - **A** `dsh-client-ui-theme/lib/client.js` 里的四段行内 CSS 绑定（rolldown inline-css 形态）各自声明多少 `--dsw-*`，并集多少；
   - **B** `exportInspectTokens()` 的静态种子 `BUILTIN_INSPECT_TOKENS` 有多少条；
   - **C** 外壳产物 CSS（`dsh-web-frontend/dist/assets/*.css`）**声明**多少 / **引用**多少 `--dsw-*`；
   - **D** 全安装树所有 client bundle 的声明并集（找 owner）。
3. 再对 A 的并集做静态 `var()` 解析（亮/暗两套表），分两种解析上下文：
   - **E** 只拿 `--dsw-*` 自洽；**F** 纳入同一批样式表里的平台变量（`--ds-*` / `--dsh-*`）。

### 观察结果（`probe/evidence/p4-theme-tokens.json`，逐字摘录）

```
A 六段行内 CSS：base=10 | corner-shape=1 | design-platform=190 | focus=2 | onboarding=7 | gradient-shadow-text=193
  并集 403 → {"font":182,"alias":107,"static":77,"specific":11,"radius":6,"elevation":5,"shadow":4,"gradient":3,"menu":2,"focus":2,"linear":2,"corner":1,"mask":1}
  亮色声明 403 条 / 暗色覆盖 196 条（其余继承亮色）
B exportInspectTokens() 静态种子 = 14 条 → {"alias":13,"specific":1}（且这 14 条全都在 A 的 403 里）
C 外壳产物 CSS：index-BPHePDI_.css 声明 2 个（alias 0）｜引用 149 个（其中 alias 55）｜vendor-*.css 0
D 全树 client bundle 声明 owner：只有一个 —— dsh-client-ui-theme(403)
E 只拿 --dsw-* 自洽解析：亮 {literal:229, resolved-chain:138, resolved-with-fallback:11, unresolved-ref:25}
                          暗 {literal:229, resolved-chain:138, resolved-with-fallback:11, unresolved-ref:25}
  25 条的悬空目标：--dsh-content-font-delta ×19、--ds-font-family-code ×6
F 纳入平台变量（24 个）后解析：亮 {literal:229, resolved-chain:164, resolved-with-fallback:10}＝403 全部落地
                              暗 {literal:229, resolved-chain:164, resolved-with-fallback:10}＝403 全部落地（0 悬空）
```

### 判定

1. **403 的出处**＝ `@deepseek-ai/dsh-client-ui-theme` 客户端产物里各段行内 CSS 声明 `--dsw-*` 的**并集**（0.2.0-rc.2 实测六段：`base` 10、`corner-shape` 1、`design-platform` 190、`focus` 2、`onboarding` 7、`gradient-shadow-text` 193）。GF19 把两段混成了一句话：`elevation`/`shadow` 来自 `gradient-shadow-text` 一段，不在 `design-platform` 里。
2. **14 的出处**＝ `exportInspectTokens()` 的静态种子，运行期再叠加"已注册主题的 token 名 + 覆盖层的 token 名"（源码原文见 `probe/evidence/p4-*.json` 的 `B_inspectDirectory.source`）。⇒ **`exportInspectTokens()` 不是 403 的全集**，它是"**带说明的目录 + 动态名**"（14 条各自带 `description`/`valueType`/`requiresLightAndDark`）。
3. **"71 个（44 alias）"**：本探针的可复算数是**外壳 CSS 引用 149 个，其中 alias 恰好 55 个**（0.1.5 一代同一口径是 115 / 44）。"71"与这两个数都对不上——两次数的口径不同（引用集合的去重面不同）。**判定：这几个数字不是同一层，不必强行对齐；本任务以本探针给出的可复算口径为准，并把它写进 lint 的实现约束。**
4. **每个 token 能否 resolve**：**能，403/403，亮暗两套都是** —— 但前提是解析上下文必须纳入平台变量（`--ds-*` / `--dsh-*` 共 24 个）。只拿 `--dsw-*` 表自洽会误判 **25 条（6%）**为悬空（19 条引用 `--dsh-content-font-delta`、6 条引用 `--ds-font-family-code`，两者都在同一批样式表里被声明）。
5. **深色载体**（原文，`probe/evidence/p5-*` 同目录）：
   - 运行期由 `dsh-client-ui-layout` 的 `ThemePresenter.apply(snapshot)` 写：`const scheme = snapshot.active.colorScheme; document.documentElement.style.colorScheme = scheme; if (scheme === 'dark') body.setAttribute('data-ds-dark-theme','') else body.removeAttribute(...)`，注释原文 **"from `active.colorScheme` (never the id — `system` is resolved upstream)"** ⇒ **按 `colorScheme` 决定，不按主题 id**。
   - 插件树激活**之前**由 ui-theme 宿主半区注入的 boot 脚本写同样两个字段：`document.documentElement.style.colorScheme = dark?'dark':'light'`、`document.body.toggleAttribute('data-ds-dark-theme', dark)`、`document.body.style.setProperty('--dsh-content-font-size','<px>')`；其中 `dark = preference==='dark' || (preference==='system' && matchMedia('(prefers-color-scheme: dark)').matches)`。
   - ⇒ **GUIFrame 判定暗色的正确姿势**＝读 `document.body.hasAttribute('data-ds-dark-theme')`（或 `documentElement.style.colorScheme`），**不要读主题 id / 不要读 preference**。
6. **对主题 lint 的实现约束**（这是本探针的真正产出，直接约束 t13）：
   - 白名单真源 = **ui-theme 样式表并集（本机 403）**，构建期可冻结；`exportInspectTokens()` 只能当"说明层/提示层"，**当白名单会把 389 个合法 token 判成未知**（噪音）。
   - 解析上下文必须包含 `--ds-*` / `--dsh-*`，否则约 6% 误报。
   - 暗色表只有 196 条覆盖、其余继承亮色 ⇒ **不要要求每个 token 都有暗色值**；要判的是"token 存在且能解析"。
   - 第三方插件可以 `register(ThemeDefinition)` / `overrideTokens(...)` 引入新 token 名 ⇒ lint **只能告警不能拒绝**（与 GB10 的"告警式"一致）。

### 残余未知 + 真机收口（P4）

- 未做：浏览器里的**运行期**取样（本探针是产物静态测量，页面没跑）。
- 收口步骤（**用户在场**，在 127.0.0.1:3080 的 DevTools 里执行）：
  1. 控制台跑 `document.body.hasAttribute('data-ds-dark-theme')`，切换主题（设置 → 外观）后重跑，确认属性随之翻转且与 `document.documentElement.style.colorScheme` 一致。
  2. 确认深色表覆盖数：在暗色下 `getComputedStyle(document.body).getPropertyValue('--dsw-alias-bg-base')` 应等于 `--dsw-static-neutral-bluish-950` 的解析值（亮色下是另一支）。
  3. 若届时能拿到客户端根 ctx（例如临时插件里打印），记录 `ctx.theme.exportInspectTokens().length`：**预期等于 14 + 已注册主题与覆盖层的 token 名数，而不是 403** —— 这条正是本探针"14 ≠ 403"的现场复核。

## P5 · 推送半边（R20）—— 判定：**mux 真实存在，但不对第三方构成可订阅面 ⇒ 阶段 1 确认退到轮询**

### 可重演步骤

1. `node probe/runtime/push-surface-probe.mjs`（对 6 个契约文件做定点抽取，写 `probe/evidence/p5-*.txt`）。
2. 逐条读 6 个判据（脚本会打印 PASS/FAIL）。

### 观察结果

```
PASS  browserRpcOpenMissing            —— 浏览器侧没有 rpc.open
PASS  muxAddressesTypertEndpoints      —— mux 的 open 寻址单位是 Typert Remote 端点
PASS  remoteEventsSingleOccupant       —— 转发事件源单占位且已注册即抛
PASS  generationSourceSoleAndStartThrows —— 连接代际源 sole + start 第二次抛
PASS  transportOpenStreamIsShellOwned  —— openStream 只在自组装传输的 shell 存在
PASS  typertRegisterIsPublic           —— Typert 注册是运行时公共 API（深路存在）
```

关键原文（各片见 `probe/evidence/p5-*.txt`）：

1. **浏览器侧 `rpc.open` 不存在**（`dsh-client-connection/lib/types/rpc.d.ts`）：
   `readonly open?: (channel, endpoint, payload, signal) => AsyncIterable<unknown>`，其文档原文 **"Open an in-process logical stream when the selected carrier supplies one. **Browser transports omit this method**; API Gateway owns their WebSocket mux."**
2. **mux 的业务形状**：host 侧 `RemoteStreamMuxServer` 挂在 **`/api/remote.mux`**（精确 WebSocket 路由，先过 `connection.requestRejection` 再 `handleUpgrade`），每条逻辑流经 `RemoteStreamOpener = (endpoint, payload, signal) => Promise<AsyncIterable<unknown>>` 由网关的 `openWireStream` 解析；客户端 `RemoteStreamMuxClient.open(endpoint, payload, signal)` 的参数文档原文是 **"@param endpoint - Typert Remote stream endpoint"** ⇒ **寻址单位是 Typert Remote 端点**，不是任意 topic。
3. **两个"可以接管"的入口都是单占位，且都被官方装配占用**：
   - `TypertGatewayService.registerRemoteEvents(source, host)`：文档 "Register the **sole** application-selected forwarded-event source … **installed by the Remote assembly**"，实现首行 `if (this.remoteEvents !== void 0) throw new Error("typert gateway: forwarded Remote event source is already registered")`。
   - 客户端 `ConnectionHandle.registerGenerationSource(source)`："Register the **sole** source defining Host generations"；`start(sinks, config)`："**API Gateway owns the loop; a second call throws**"。
4. **客户端命名空间来自装配选择**：`dsh-api-gateway/lib/types/client/index.d.ts` 首行原文 "Client projection of generated Typert Remote descriptors. Contributions install traced `remote.<namespace>` services"；客户端 `ClientRemoteService` 按 `direct`/`scoped` 两组**贡献**挂载命名空间（`const namespaces = new Set([...direct.keys(), ...scoped.keys()])`，见 `p5-namespaceSetBuild.txt`）。第三方插件注册的 host 侧描述符**不会自动出现在页面投影里**。
5. **普通页面塞不进自己的流载体**：唯一注入点 `__DSH_TRANSPORT__.openStream` 的文档原文 **"Worker-local Gateway stream carrier; absent when the page uses the Gateway WebSocket"** ⇒ 服务式页面（我们这种）根本没有这个字段。
6. **唯一名义可行的深路**：`ctx.typert.register(contribution)`（`@deepseek-ai/dsh-typert-registry` 的公共运行时 API，`TypertRegistryContract` 里有 `register/get/resolve/list/...`）+ 自己写 host 流方法 + 自己组织客户端投影。这条路上要吃掉：Typert 描述符协议、客户端装配、以及和上面两个单占位入口的关系。

### 判定

1. **API Gateway 的 WebSocket mux 不是给第三方插件的订阅面**：它有真实的推送载体（心跳、逻辑流多路复用、代际重连），但**寻址单位是 Typert Remote 端点**、**入口单占位已被官方装配占着**、**浏览器侧 `rpc.open` 明文不提供**、**普通页面连流载体注入点都没有**。
2. ⇒ **阶段 1 确认退到「请求/响应 + 轮询」**（与 GS11 ⑥ 既定口径一致）。GUIFrame 的数据通道按 t13 的既定范围做，不引入推送依赖。
3. **阶段 2 若想要推送，代价清单**（写给未来的自己，不是现在做）：需要 (a) host 半区用 `ctx.typert.register` 注册自己的流端点/事件描述符；(b) 解决客户端投影（装配选择 / 自建 namespace service）；(c) 与官方"单占位"入口共存（不能抢 `registerRemoteEvents`，只能用官方那条源，或者只在 unary/intercept 面上做增量）；(d) 承担 Typert 协议的版本耦合（`0.2.0-rc.2` 是 rc 线）。**在这四条被评估之前，不要承诺"有推送"。**
4. **对 t13 的额外收益（顺带确认）**：宿主侧 `ctx.connection.fetch.register` 那条**精确 Fetch 路由**（阶段 1 的诊断上报要用的）与 mux 无关，且已在 t4 的 P2 里机检过（`/api` 共享通道同进程分派 + 平台自身 `installFailLoud` 先例）。

### 残余未知 + 真机收口（P5）

- 未做：真机上"是否有活动 WS 升级、升级到哪"的现场观察（不碰在跑进程，故没去连）。
- 收口步骤（**用户在场**）：
  1. 打开 127.0.0.1:3080，DevTools → Network → WS：**预期能看到 `ws://127.0.0.1:3080/api/remote.mux` 的 101 升级**（这就是 mux 的实物；没有它说明该会话未开 stream/event）。

  3. 若要更硬的：在临时插件里打印 `ctx.get('connection')?.rpc?.open`，预期 `undefined`。
